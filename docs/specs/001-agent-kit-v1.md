# 001: agent-kit v1

## Goal

Make my AI agent setup portable and tool-agnostic.
On any machine, cloning one repo and running one script gives Claude Code and Gemini CLI the same rules, commands, reviewer, hooks, and skills.
Projects opt in and receive stack-specific rules and checks, and stay self-contained.

## Decisions

- Tools: Claude Code (primary), Gemini CLI (secondary). One tool-agnostic source, one adapter per tool.
- Two repos: `agent-kit` (this one) and `fastapi-nextjs-starter` (project scaffolding).
- The old orchestrator system is retired and preserved under the git tag `legacy-orchestrator`.
- Tiers: global (stack-free), stack (nextjs, fastapi), project (lives in each project).
- Stacks attach per directory, not per repo.
- Global tier is installed by per-item symlinks. `settings.json` is merged, never linked.
- Third-party skills are vendored in `vendor/skills/` and recorded in `vendor/skills-lock.json`.
- Hooks are opt-in per project through `.agent-kit.json`.
- Tool-specific enforcement where available (Claude Code hooks). `verify.sh` through git pre-commit and CI is the universal enforcement layer for every tool.

## Non-goals (v1)

- Vite and Java Spring stacks.
- `kit new-project` (comes after the starter repo is improved).
- Syncing a project to an older tagged kit version.
- Automatic updates of vendored skills.
- Codex CLI and Cursor adapters (the adapter interface must allow them later).
- Windows support.

## Acceptance criteria

- KIT-1: The repo contains only agent-kit content. Scaffolding lives in `fastapi-nextjs-starter`. Everything removed is recoverable from `legacy-orchestrator`.
- KIT-2: On a machine with git and jq, `git clone` plus `./install.sh` installs the global tier for every detected tool: context file, commands, reviewer agent, hooks, and skills.
- KIT-3: `install.sh` is idempotent. Existing files are backed up before being replaced, never silently overwritten. `--uninstall` removes only kit links and restores backups. `--dry-run` changes nothing.
- KIT-4: Adding a tool requires adding one file in `adapters/` and nothing else.
- KIT-5: Adding a stack requires adding one folder in `stacks/` that follows the stack contract, and nothing else.
- KIT-6: Every rule exists in exactly one place in the repo.
- KIT-7: The global tier contains no contradictory rules. The resolutions in the plan are applied.
- KIT-8: `global/AGENTS.md` is stack-free and at most 150 lines (checked by `scripts/verify.sh`).
- KIT-9: Global hooks exit 0 in projects without `.agent-kit.json`. In opted-in projects they block test edits (unless `ALLOW_TEST_EDITS=1`) and enforce the 3-failure stop rule through the project's `scripts/verify.sh`.
- KIT-10: `kit sync` installs the configured stacks per directory, preserves project content outside generated markers, makes the project self-contained, installs a pre-commit hook without overwriting an existing one, and records the kit version. A second sync produces no diff.
- KIT-11: `kit doctor` reports broken links, missing dependencies, and version drift.
- KIT-12: `scripts/verify.sh full` passes, including hook, install, and sync tests, and runs in CI on Linux and macOS.
- KIT-13: All scripts run on macOS default bash 3.2 and on Linux.
- KIT-14: The README explains installing in at most 3 commands, updating, opting a project in, adding a tool, stack, or skill, and uninstalling.

## Constraints

- Dependencies: bash, git, jq. shellcheck optional.
- Bash 3.2 compatible: no associative arrays, no `mapfile`, no `${var,,}`, no GNU-only flags (`sed -i` must work on both BSD and GNU).
- No secrets anywhere in the repo.
- Generated files carry a header: generated by agent-kit, version, do not edit.

## Stack contract

Every `stacks/<name>/` contains:

- `rules.md`: rules true for every project on this stack, max 80 lines.
- `lint/`: a preset the project's lint config extends.
- `verify.sh`: this stack's checks, with `fast` and `full` modes.
- `registry.sh`: writes the inventory to `docs/inventory/<name>.md` in the target directory.

## Integrity rules (go into global/AGENTS.md)

1. Never modify tests, expected outputs, snapshots, or fixtures to make checks pass. A failing test means the implementation is wrong until proven otherwise.
2. Never weaken a check: no `Any` or `as any`, `type: ignore`, `ts-ignore`, `noqa`, `eslint-disable`, skip or xfail, loosened assertions, or broad exception handling that swallows errors.
3. Never change a function's output, signature, or return type just to satisfy a check. Fix the logic that produces it.
4. Fix the root cause, not the symptom.
5. Stop rule: if the same check still fails after 3 genuine attempts, stop. Report the exact error, what you tried and why each attempt failed, your root-cause hypothesis, and what you need.
6. If you believe a test itself is wrong, do not edit it. Stop, explain why, and let the user decide.
7. When resolving merge or rebase conflicts, preserve the intent of both sides. Never take one side wholesale without explaining what the other side did and why it is safe to drop. Run `scripts/verify.sh full` after resolving.

## Hook behavior

- `protect-tests.sh` (before Edit, Write, MultiEdit): blocks edits to test, snapshot, and fixture files unless `ALLOW_TEST_EDITS=1`. Exit 2 with a message telling the agent to stop and ask if it believes the test is wrong.
- `check-with-limit.sh fast|full` (fast after edits, full on Stop): runs the project's `scripts/verify.sh <mode>` if it exists and is executable. Counts consecutive failures per session and mode. On failures 1 and 2: exit 2 with the output and "fix the root cause, do not weaken checks". On failure 3: exit 2 with the stop-rule message. After that: exit 0 so the agent can report. A pass resets the counter.
- Both hooks append events (date, event, branch, mode) to `agent-metrics.tsv` in `$(git rev-parse --git-common-dir)`, which is shared by all worktrees and never committed.
